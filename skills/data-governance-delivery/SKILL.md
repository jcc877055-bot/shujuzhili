# 企业数据资产治理与数据质量闭环管理系统全流程交付

## 固定项目基线

- 项目：企业数据资产治理与数据质量闭环管理系统
- 类型：PC 端 Web 企业管理系统
- 前端：Vue 3、Vite、Element Plus
- 后端：Java 17、Spring Boot 3
- 数据库：MySQL 8
- 架构：前后端分离、RESTful API、Git 管理
- 业务结构：B0 企业数据资产治理与数据质量闭环业务；B1 组织账号与权限治理；B2 数据源接入与元数据采集；B3 数据资产目录与数据标准管理；B4 数据质量规则与质量检测；B5 数据质量问题工单闭环；B6 审计与数据治理看板。

## 权威事实源

每次执行先定位并读取以下内容，禁止凭记忆编造：

1. `总任务台账.md`：任务状态、依赖和交付范围的总入口。
2. `docs/`：软件工程文档事实源；递归盘点实际文件，不预设恰好有 27 个。
3. 前端、后端、数据库脚本、测试与部署目录：实现证据事实源。
4. Git 状态与提交历史：版本证据事实源。

若台账、文档和代码冲突，记录冲突，不擅自选择其一。默认优先级为：已验证运行结果 > 当前代码/脚本 > 已批准或基线化文档 > 草稿 > 台账中的文字状态。

## 总执行规则

1. 先盘点，后修改；先文档，后实现；先测试设计，后编码。
2. 一次只推进用户指定阶段；未指定时从最早未通过质量门禁的阶段开始。
3. 每阶段必须执行“读取输入 → 生成/更新交付物 → 完整性检查 → 一致性检查 → 更新追踪矩阵 → 更新总任务台账 → 汇报结果”。
4. 上一阶段未通过时，不进入下一阶段；列出缺项并先补齐。
5. 所有结论必须给出文件、代码、测试输出或运行结果作为证据；找不到证据就标记“未验证”，不得写“已完成”。
6. 保留现有人工内容；修改前检查未提交变更，不覆盖无关内容。
7. 图表优先保留 Mermaid、PlantUML、draw.io 等可编辑源文件，并提供可查看版本。
8. 每份文档至少包含：文档编号、名称、版本、状态、输入依据、输出结果、关联需求编号、变更记录。

## 启动盘点

执行任何阶段前，产出或更新 `docs/00-项目管理/文档资产清单.md`，至少包含：

| 字段 | 要求 |
|---|---|
| 序号 | 连续编号 |
| 文件路径 | 仓库相对路径 |
| 文档编号/名称/版本 | 从文档正文提取；缺失则标记 |
| 所属阶段 | S01-S11 |
| 关联 B/UR/FR/NFR/API/DB/TC 编号 | 没有则标记缺失 |
| 状态 | 未开始/草稿/待评审/已基线/已验证 |
| 输入依据 | 可追溯来源 |
| 输出/证据 | 文件、图、代码或测试结果 |
| 缺项与冲突 | 具体说明 |

同时统计文件总数、核心文档数、空文件、重复文档、断链、缺编号、缺版本、缺输入依据、缺输出结果和缺关联需求编号。不得只依据文件数量判断完成。

## 阶段与门禁

### S01 总任务台账与项目目录

做什么：读取现有台账和目录；补齐任务编号、输入、输出、完成标准、依赖、状态、证据路径、负责人/角色、风险；建立目录和文档资产清单。

交付：`总任务台账.md`、项目目录说明、文档资产清单、缺项清单。

门禁：四个课堂报告、Skill、业务案例、原型、代码、测试、部署、Git 和 12/27 份文档均有任务项；所有“已完成”都有证据。

### S02 四个课堂报告

按顺序完成：

1. 《软件需求表达工具调研报告》：比较互联网应用软件、企业管理软件、工具软件；覆盖访谈、用户故事、用例、流程图、泳道图、状态图、决策表、原型、追踪矩阵、接口契约、测试用例。
2. 《软件需求管理方案》：覆盖来源、调研、会议、角色、编号、优先级、评审、基线、变更、影响分析、成果、版本和追踪，并含模板与项目示例。
3. 《原型设计方法与实施方案》：说明目标、输入输出、步骤、评审与达标标准；至少 10 个 PC 页面，每页写角色、功能、字段、按钮、交互、异常提示和验收点。
4. 《AI辅助软件开发全流程 Skill 说明书》：说明目录、触发、阶段输入输出、质量门禁、追踪、防漏项与防编造机制，并给项目指令示例。

交付：四份报告、引用/图表源文件、四项报告核查表。

门禁：按“老师要求—已完成—缺失—待补图表/案例—是否适合第一次汇报”逐项检查；缺项补齐前不进入系统开发。

### S03 业务定位与全局业务基线

做什么：明确背景、痛点、目标、对象、价值承担方、参与者、核心业务对象、范围、边界和定位；建立 B0、B1-B6 结构树、角色职责、总体流程、一级板块流程和开放问题台账。

交付：业务定位说明、业务结构图、总体流程图、角色职责表、核心对象表、开放问题台账。

门禁：能回答谁参与、围绕什么对象、解决什么痛点、产生什么价值、哪些属于范围内/外；本阶段不提前写页面和代码。

### S04 首个垂直业务闭环

做什么：详细分析“问题发现—派单—整改—复检—关闭”。

交付：详细流程图、泳道图、状态图、角色活动矩阵、规则表、异常处理表、信息流转表、指标、确认清单及可编辑图源。

门禁：正常、驳回、重开、超期、撤销、重复问题、权限异常均有路径；形成业务基线 V0.1。

### S05 系统需求与追踪

做什么：把业务基线转换为角色、功能、非功能、权限、数据、审计、接口、页面、规则、异常和验收需求；建立唯一编号。

交付：软件需求规格说明书、术语表、用例规格、需求评审记录、需求追踪矩阵。

门禁：关键需求使用稳定编号（如 `FR-AUTH-001`、`FR-QUALITY-001`），且追踪链完整：`痛点 → 用户需求 → FR/NFR → 页面/模块/表/接口 → TC → 验收结果`。

### S06 测试前置

做什么：在编码前设计测试计划、场景、用例、数据和验收标准。

交付：测试计划、测试场景、测试用例、测试数据说明、验收标准、需求—测试覆盖表。

门禁：关键需求至少一个测试用例；覆盖正常流程、越权、异常、超期、复检退回、审计日志，并明确前置条件、步骤、期望结果和编号。

### S07 PC Web 原型验证

做什么：基于需求和测试设计页面导航及可验证原型，重点澄清需求。

交付：页面清单、导航图、原型说明、可查看原型、原型评审记录。

至少覆盖：登录、工作台、组织账号权限、资产目录、元数据详情、数据标准、质量规则、检测任务、质量问题、治理工单、审计日志、治理看板。

门禁：每页标明可见角色、字段、按钮、交互、状态、空态、加载、成功和异常提示、关联需求与验收点；关键流程可从入口走到闭环。

### S08 详细设计

做什么：依据需求、测试和原型完成总体架构、模块、数据库、接口、权限、审计、异常、部署和目录设计。

交付：架构设计、模块设计、ER 图、表设计、API 设计、权限矩阵、审计设计、异常码、部署设计、前后端目录设计。

门禁：模块、接口、表与需求编号能互相追溯；状态机和事务边界明确；敏感操作有授权与审计；设计能支撑测试用例。

### S09 代码仓与分模块实现

做什么：建立 Vue 3 前端、Spring Boot 3 后端、MySQL 初始化脚本、README、环境说明与分支规范；先实现 B1 和 B5，再实现 B2/B3、B4、B6。

交付：可构建源码、数据库脚本、配置样例、README、分支规范、模块实现记录、单元/接口测试代码与结果。

门禁：不得仅生成空骨架或静态页面；功能关联需求、API 和 TC 编号；构建、单元测试、接口测试通过；失败项如实记录。

### S10 系统测试、部署与验收

做什么：执行功能、权限、异常、闭环、审计和基本性能测试；修复并回归；准备部署、运维、用户操作、演示数据和验收材料。

交付：缺陷清单、修复记录、回归记录、系统测试报告、部署方案/手册、用户手册、运维手册、演示数据、验收报告。

门禁：关键需求均有设计、代码、测试和验收证据；阻断缺陷清零；部署步骤经实际验证或明确标记未验证。

### S11 文档补齐与最终审计

做什么：按文档资产清单先保证至少 12 份核心文档完整，再补齐目标 27 份；审计全项目。

交付：更新后的 27 份文档、文档资产清单、最终审计报告、最终汇报清单。

门禁：文件数量、编号、版本、输入、输出、关联需求与正文质量全部通过；最终报告列出已完成项、缺失项、风险项、修复优先级和汇报清单。

## 每轮工作输出格式

每完成一个阶段，向用户报告：

1. 本轮阶段与结论。
2. 新建/修改文件（路径 + 用途）。
3. 已通过的验收项。
4. 未通过项、风险与证据缺口。
5. 台账与追踪矩阵更新位置。
6. 是否允许进入下一阶段；若不允许，列出必须先完成的事项。

## 防漏项与防编造检查

- 文档存在不等于内容完成；必须读取正文。
- 代码存在不等于功能可用；必须构建、测试或运行验证。
- 页面存在不等于闭环完成；必须验证角色、状态和异常路径。
- 测试用例存在不等于测试通过；区分“已设计、已执行、通过、失败、阻塞”。
- Mermaid/截图不能替代可追踪的需求和验收证据。
- 不虚构访谈对象、会议结论、测试结果、性能数字、部署成功或 Git 提交；无证据即标记待确认/未执行。
- 删除、覆盖、发布、创建远程仓库或写入外部系统前，确认用户授权。
